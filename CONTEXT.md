# Babel FIRE — Durable Supporting Context

**Purpose:** preserve supporting context that materially helps FIRE product/design work without becoming a second live specification.

Start every FIRE continuation with `START_HERE.md`, then follow `AGENTS.md` authority. `FIRE_CORE.md` owns current cross-generation doctrine. `V6.md` owns live V6 production behavior. `V7_DRAFT.md` owns current G7 shell behavior.

This file must **not** contain route-by-route G7 rules, current PR/SHA status, or “LOCKED” implementation language that can become stale. Git history preserves the much larger historical context file and retired implementation details.

## 1. Product identity / ancestry

- **Babel** = parent creative identity/ecosystem.
- **FIRE** = the music-production companion product.
- Inside the app, using simply `FIRE` is usually appropriate.
- The FIRE reasoning loop is **Feel → Identify → Reason → Experiment → Evaluate**.
- FIRE grew partly from the earlier Smithereens production-study work, but it is no longer a Smithereens-specific study app.
- Smithereens and other references are projects/workflows inside FIRE; they are not FIRE's visual identity.

FIRE's canonical purpose/boundaries live in `FIRE_CORE.md`.

## 2. Reference musician context relevant to product design

Babel is an experienced musician/multi-instrumentalist with strong arrangement/performance instincts and solid working production knowledge.

Comfortable working concepts include:

- EQ
- compression
- headroom
- panning
- automation
- masking
- reference listening
- basic spatial effects / reverb / delay
- direct vs ambient sound
- static balance

Do not design FIRE as though the reference musician is a total beginner.

The larger development opportunity is **consistent production judgment and finishing**: knowing where to go next, diagnosing why a record differs from the target/intention, sequencing work well, and finishing/mixing reliably.

Important product implication: FIRE itself must still adapt from true beginners through advanced producers. Never hard-code the reference musician's experience as the user model for everyone.

## 3. Interaction / working preferences that materially affect FIRE

Preserve these across chats:

- concise, manager-style direction
- one obvious useful next action
- small concrete tasks rather than giant abstract assignments
- rigorous logic underneath a calm/simple interface
- applied learning through real music
- explain **why** when it improves judgment
- `I don't know` / `Not sure` must be valid
- preserve creative authorship; FIRE guides decisions rather than making art for the musician
- avoid repetitive bureaucracy and over-explaining
- physical-device feedback outranks theoretical visual polish
- iPhone/iPad should expose the same product logic/hierarchy/actions/states even when presentation adapts
- roughly **70% calm Apple-like hierarchy / 30% focused creative-tool density** remains a useful visual target, not a formula
- Basecamp is useful as a reference for substantial content/actions without overwhelm, not as a layout to copy
- simple, durable one-word naming is preferred where it genuinely carries the concept

## 4. Core production problem FIRE should solve

The musician should not leave a FIRE session merely having organized FIRE.

FIRE should help convert vague reactions such as:

> “This doesn't sound professional.”

into useful production understanding such as:

> “The vocal is losing hierarchy because the midrange support is masking it; try this specific balance/arrangement experiment, then evaluate the result.”

The product should strengthen:

- critical listening / diagnosis
- arrangement judgment
- source/performance decisions
- balance/hierarchy
- tone/frequency decisions
- dynamics/punch
- width/depth/space
- movement/automation
- finishing
- comparison without endless perfection loops

## 5. One FIRE brain, two real project contexts

Detailed doctrine lives in `FIRE_CORE.md`; preserve the practical distinction here:

### Original

The musician's intention defines the target. Guidance can provide a strong order of operations while preserving experimentation and authorship.

### Recreation

A **standalone cover/reconstruction workflow** whose target comes from the reference plus the musician's relationship to it.

Recreation may be faithful Match, Interpretation, Reimagination, or a production study. It is not a secondary learning mode and does not require Original.

Learning can emerge from Recreation, but someone may also use it simply to finish covers efficiently.

## 6. Recreation phase ancestry

The long-running Recreation framework remains useful conceptual ancestry:

1. **The Map** — understand the reference
2. **The Skeleton** — build a complete rough song
3. **The Sounds** — sources, performances, tone
4. **The Balance** — hierarchy through level/pan
5. **The Shape** — EQ, dynamics, transients, saturation/character
6. **The World** — depth, width, reverb, delay, movement
7. **The Finish** — compare, revise, polish, complete

These are strong grouping concepts, not permission to restore old V6 Step/Checkpoint/Roadmap UI into G7.

Current G7 shell behavior is exclusively defined in `V7_DRAFT.md`.

## 7. Original conceptual phase ancestry

Current conceptual Original journey to breadboard/test:

1. **The Spark** — capture/protect the idea
2. **The Direction** — intent, energy, mood, references if useful
3. **The Skeleton** — complete rough song
4. **The Production** — arrangement, transitions, layers, textures, production identity
5. **The Recording** — intentional performances replacing placeholders
6. **The Mix** — Balance → Shape → World as useful sub-structure
7. **The Finish** — compare, revise, final mix/master/commit

This is conceptual architecture, not a locked page list. FIRE Core breadboarding may merge, rename, reorder, or reshape surfaces if the product works better.

## 8. Shared decision sequencing hypothesis

Useful default production sequence:

**Intent → Arrangement → Performance/source → Balance → Tone/dynamics → Space → Movement → Final comparison → Finish**

This is guidance, not a creative prison. Diagnosis may reopen upstream work.

Sparse arrangements are valid. Never recommend an instrument/layer merely because convention expects it; every addition needs a musical job.

## 9. Companion boundary / what to remember

FIRE should retain meaning that a DAW usually does not understand well:

- intention/hierarchy
- perceived issue
- diagnosis
- meaningful experiment + result
- accepted decision/difference
- unresolved problem
- reusable lesson
- next useful production decision

Logic/DAW remains the owner of detailed regions/takes, routing, plugin values, exact automation values, and mixer/session mechanics unless a future feature proves specific data genuinely necessary.

Default rhythm remains:

**FIRE → Logic → FIRE → Logic**

## 10. Track → Element → Role hypothesis

Still useful to test during FIRE Core work:

- **Track** — represented DAW/recorded part
- **Element** — perceptual production object, possibly composed of multiple tracks
- **Role** — musical/perceptual job such as focal point, pulse, low-end movement, atmosphere, width, texture

Purpose: reason at listener-perception level without rebuilding Logic's mixer.

Exact data/UI is deliberately not locked.

## 15. Historical implementation lessons worth retaining

### The Map prototype taught useful things

The most-developed early workflow centered on understanding structure, track palette, section activity, changes, unresolved questions, and takeaways before deep production decisions.

Useful durable lessons:

- stable section identity matters when sections reorder/edit
- arrangement/form should be understood before downstream work depends on it
- project data should be entered once and reused intelligently
- each phase should make the next phase smarter
- if a field does not improve a current decision or useful downstream reasoning, delete it
- structured listening is useful; excessive form entry is bureaucracy

Do not use these lessons to restore superseded V6 UI patterns.

### V6 remains valuable production history

V6 is still live production until G7 is deliberately promoted. Its detailed behavior and compatibility requirements remain in `V6.md` and code/tests.

Do not copy V6 Phase Home, Step/Checkpoint, center navigator, or Roadmap behavior into G7 unless a new decision explicitly earns it.
