**Purpose:** preserve supporting context that materially helps FIRE product/design work without becoming a second live specification.

This file must **not** contain route-by-route G7 rules, current PR/SHA status, certification-category status, or “LOCKED” implementation language that can become stale. Git history preserves the larger historical context and retired implementation details.

## Product identity / ancestry

- **Babel** = parent creative identity/ecosystem.
- **FIRE** = the music-production companion product.
- Inside the app, using simply `FIRE` is usually appropriate.
- The FIRE reasoning loop is **Feel → Identify → Reason → Experiment → Evaluate**.
- FIRE grew partly from the earlier Smithereens production-study work, but it is no longer a Smithereens-specific study app.
- Smithereens and other references are projects/workflows inside FIRE; they are not FIRE's visual identity.

FIRE's canonical purpose/boundaries live in `FIRE_CORE.md`.

## Reference musician / working context

Babel is an experienced musician/multi-instrumentalist with strong arrangement/performance instincts and solid working production knowledge. Do not design FIRE as though the reference musician is a total beginner.

The larger development opportunity is consistent production judgment and finishing: knowing where to go next, diagnosing why a record differs from the target/intention, sequencing work well, and finishing/mixing reliably.

FIRE itself must still adapt from true beginners through advanced producers; never hard-code the reference musician's experience as the user model for everyone.

Useful working preferences:

- concise, manager-style direction
- one obvious useful next action
- small concrete tasks rather than giant abstract assignments
- rigorous logic underneath a calm/simple interface
- applied learning through real music
- explain **why** when it improves judgment
- `I don't know` / `Not sure` must be valid
- preserve creative authorship; FIRE guides decisions rather than making art for the musician
- avoid repetitive bureaucracy and over-explaining
- physical-device feedback outranks theoretical visual polish
- iPhone/iPad expose the same product logic/hierarchy/actions/states even when presentation adapts
- roughly **70% calm Apple-like hierarchy / 30% focused creative-tool density** remains a useful visual target, not a formula
- Basecamp is useful as a reference for substantial content/actions without overwhelm, not as a layout to copy
- simple, durable one-word naming is preferred where it genuinely carries the concept

## Shell-completion context

G7 shell work now has a finite certification contract rather than an open-ended “keep polishing screens until they feel done” loop.

The target is reusable grammar, not frozen fixture screens. A future FIRE section/modal should inherit solved fundamentals and feel like Babel without re-deciding typography, spacing, surfaces, action hierarchy, accessory geometry, responsive rules, or temporary-UI composition from scratch.

Current Setup → Structure → Tracks is disposable stress-test fixture content. It can change when useful to exercise the shell and must not become FIRE Core architecture merely through polish.

A developer-only Shell Test inside G7 uses actual G7 primitives to expose systemic defects across representative states/densities. It is not Babel Lab and not a second FIRE implementation.

Shell freeze means the foundation is stable enough to build confidently, not that the design system can never gain a genuinely new primitive. FIRE Core may later extend the smallest necessary part deliberately.

Detailed category definitions/freeze requirements live in `G7_SHELL_CERTIFICATION.md`; current category status/evidence lives in `G7_SHELL_CERTIFICATION_STATUS.md`.

## Core production problem FIRE should solve

The musician should not leave a FIRE session merely having organized FIRE.

FIRE should help convert vague reactions such as “this doesn't sound professional” into useful production understanding: identify the meaningful issue, explain likely cause/tradeoff, propose a specific DAW experiment, and evaluate the result.

The product should strengthen critical listening/diagnosis, arrangement, source/performance decisions, balance/hierarchy, tone/frequency, dynamics/punch, width/depth/space, movement/automation, finishing, and comparison without perfection loops.

## One FIRE brain, two real project contexts

### Original

The musician's intention defines the target. Guidance can provide a strong order of operations while preserving experimentation and authorship.

### Recreation

A standalone cover/reconstruction workflow whose target comes from the reference plus the musician's relationship to it. Recreation may be faithful Match, Interpretation, Reimagination, or a production study. It is not a secondary learning mode and does not require Original.

## Conceptual phase ancestry

Recreation ancestry remains useful grouping evidence: **The Map → The Skeleton → The Sounds → The Balance → The Shape → The World → The Finish**.

Original conceptual ancestry to breadboard/test remains: **The Spark → The Direction → The Skeleton → The Production → The Recording → The Mix → The Finish**.

These are conceptual architecture, not locked page lists. Do not restore old V6 UI or infer G7 fixture routes from them.

Useful shared sequencing hypothesis:

**Intent → Arrangement → Performance/source → Balance → Tone/dynamics → Space → Movement → Final comparison → Finish**

This is guidance, not a creative prison. Diagnosis may reopen upstream work. Sparse arrangements are valid; every recommended addition needs a musical job.

## Companion boundary / what to remember

FIRE should retain meaning a DAW usually does not understand well: intention/hierarchy, perceived issue, diagnosis, meaningful experiment/result, accepted decision/difference, unresolved problem, reusable lesson, and next useful production decision.

Logic/DAW remains owner of detailed regions/takes, routing, plugin values, exact automation values, and mixer/session mechanics unless a future feature proves specific data necessary.

Default rhythm: **FIRE → Logic → FIRE → Logic**.

## Track → Element → Role hypothesis

Still useful to test during FIRE Core work:

- **Track** — represented DAW/recorded part
- **Element** — perceptual production object, possibly composed of multiple tracks
- **Role** — musical/perceptual job such as focal point, pulse, low-end movement, atmosphere, width, texture

Purpose: reason at listener-perception level without rebuilding Logic's mixer. Exact data/UI is deliberately not locked.

## Learning / skill-model context

FIRE should adapt by domain, not label the whole musician Beginner/Intermediate/Advanced. Strong skill evidence comes from intentional decisions, successful diagnosis/evaluation, independence, transfer, and repeated application—not taps or page completion.

Likely evidence ladder remains a hypothesis: **Encountered → Guided → Independent → Transfer → Consistent**.

Future cross-app evidence semantics live in `BABEL_PLATFORM.md`; sibling-app concepts live in `BABEL_APPS.md`.
