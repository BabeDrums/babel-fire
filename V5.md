# Babel FIRE V5 — Interaction Redesign Specification

## Why V5 exists
V4 proved that the continuous timeline model works, but real use exposed too much friction and too much prototype-looking UI. V5 should keep the strong engine and substantially redesign the experience.

The goal is not a cosmetic patch. Keep the timeline architecture, data continuity, and downstream logic; redesign the interaction layer so it feels deliberate, touch-first, calm, and polished.

## Core principle
**FIRE assumes the music keeps doing what it was doing. The user documents only meaningful change.**

A detailed underlying model must not create a detailed-looking default interface.

---

# 1. Map the Form

## Current problem
V4 uses separate steps for selecting a section type and selecting its bar count, and it shows redundant bar readouts after the value is already visually selected.

## V5 behavior
Use one sheet / one uninterrupted flow.

The sheet should contain:
- section type options: Intro, Verse, Pre-Chorus, Chorus, Bridge, Instrumental, Outro, Custom
- bar-length choices: 4, 8, 12, 16, plus Custom
- one Add Section action

Requirements:
- A section is not inserted until both type/name and length are valid.
- Repeated standard names continue to auto-number.
- Custom exposes a name field only when selected.
- Selecting a bar pill is sufficient visual confirmation. Do not add a separate `4 bars` readout beside/below it.
- Never show broken copy such as `Bars bars`.
- Keep permanent drag handles for reordering after sections are created.
- Row tap may still expose Rename / Length / Remove as a compact edit sheet.
- Structure verification still exists after the list.

Design this screen as a cohesive section builder rather than two forms glued together.

---

# 2. Arrangement visual redesign

## Direction
Do not make the arrangement look like a spreadsheet or DIY sequencer.

Aim for a compact touch timeline:
- restrained section surface
- subtle ruler / bar guides
- stronger musical objects than grid decoration
- clean spacing
- rounded, intentional ranges
- minimal borders
- no unnecessary explanatory copy
- fixed track lane ordering across sections so tracks do not jump vertically during section transitions

The section-to-section slide remains. Continuous ranges should visually feel continuous.

## Collapsed track row
Show:
- track name
- compact presence visualization
- compact visual encoding of mapped changes

Do NOT show textual summaries such as:
- `1 change`
- `2 changes`
- `Starts bar 3`
- similar narration that the timeline already communicates

A collapsed row must still visually reflect duration changes / markers. Expanding a track is for editing, not for making the information exist.

## Touch targets
Visible lines may be visually thin, but their actual hit areas must be generous.

The user must never be required to accurately tap a 4–8px line.

Prefer:
- the entire meaningful row area as a selection target
- large invisible hit regions around handles
- explicit change chips/buttons for selecting a mapped change

---

# 3. Presence model and editing

## Continuity
Presence is open-ended by default.

When a user adds an absent track in the current section:
- it begins at the start of the current section by default
- it has no end until the user explicitly shortens/stops it
- it therefore continues through every later section
- if later sections are added, the open presence continues through them too

The user edits the exception, not the default.

## Adding
When a track is absent, a clear `+` affordance adds presence immediately. Do not ask whether it continues into the next section.

## Editing
Remove the dedicated **Cut** button and the modal that asks for a bar to cut.

Primary interaction:
- tap/select the track/range using a generous row-sized hit area
- selection reveals clear but restrained start/end handles
- dragging the left/right handle trims or extends the presence
- snapping is whole-bar in V5
- show lightweight position feedback while dragging

No ugly blue cap/highlight. Selection should be understated and intentional.

A double-tap or long-press may be supported as a shortcut only if useful, but no essential behavior may depend on an undiscoverable gesture.

If a true internal gap/re-entry needs a split, expose Split only contextually after selection rather than leaving a permanent Cut button in the UI.

Adjacent presence ranges with no actual gap should merge.

---

# 4. Add Change redesign

## Current problem
V4 exposes implementation concepts and nested decisions:
- category first
- then action
- duration vs moment concepts
- timing prompts
This makes simple observations feel bureaucratic.

## V5 add flow
`+ Change` opens ONE clean sheet.

All common actions are visible immediately, grouped only by small visual headings. Do not require category drill-down like `Space → Widens`.

Suggested set:

### WIDTH
- Widens
- Narrows

### LEVEL
- Louder
- Softer

### PERFORMANCE
- Doubles
- Pattern shift
- Register shift

### SOUND
- Effect shift

The exact visual grouping can be refined for clarity, but the user should be able to see and choose `Widens` directly from the first screen.

Remove **Transition cue** from V5. It is not defined clearly enough to justify space.

Do not ask the user to classify a change as Duration or Moment. That distinction is internal behavior.

---

# 5. Default change behavior

Choosing a change should immediately create it without asking start/end-condition questions.

For a track change:
- create it across the applicable current visible presence by default
- preserve the continuity model so state-like changes may continue forward until trimmed or superseded where appropriate
- close the add sheet
- let the user refine timing directly on the visual timeline

Do not make the creation flow ask for start/end bars.

Same-category incompatible states should resolve automatically:
- e.g. a later `Narrows` should end/supersede an active `Widens` state at that musical position rather than creating contradictory overlap

Different categories may overlap.

---

# 6. Selecting and editing mapped changes

## Current problem
Trying to tap a skinny duration line is finicky. The menu that appears after tapping a line is confusing and repeats information already visible on the grid.

## V5 behavior
The colored line is primarily a visualization, not the only control.

When a track is expanded, provide clean, sufficiently large change selectors/chips for its mapped changes, for example:
- `Widens`
- `Louder`
- `+ Change`

Tapping a change chip/selectable item:
- selects that change on the visual timeline
- reveals timing handles directly on its range when timing is editable
- exposes only truly necessary actions, principally Remove
- does NOT open a redundant details menu repeating type/start/end information

Removing a change should be simple and reversible. Prefer an immediate removal plus Undo rather than a confirmation modal for routine edits.

The `+ Change` sheet may also visually indicate already-active options so the user can understand what is already mapped without hunting for lines.

---

# 7. Change visualization

FIRE itself should use a neutral premium dark palette. Musical information may use restrained category colors.

Requirements:
- presence remains visually primary and neutral
- change categories may use distinct restrained colors
- color is not the only distinction: use position, thickness, shape, or marker/range form as well
- two changes plus presence must still look calm, not like three competing neon tracks
- subordinate change visuals should feel attached to their parent track
- only one track expands at a time
- no odd colored cap appears merely because a track is focused

The collapsed lane should preserve enough of these visual cues to understand the arrangement without expanding it.

---

# 8. Mix/global changes

Do not force section-wide changes onto an instrument.

Keep Mix/global capability, but make it visually quiet. Do not let an empty Mix lane dominate the default view. A global-change affordance can remain discoverable without permanently consuming the same visual weight as an active instrument track.

---

# 9. Feel / Focus / Notes

Do not unnecessarily redesign working controls just because V5 redesigns Arrangement.

Keep:
- Feel dimensions and their mutually exclusive choices
- Focus / No clear focus
- Notes / Parking Lot / Takeaway
- Section Study progression and final Map review logic

Polish visual consistency as needed, but avoid scope creep.

---

# 10. Data / architecture

The continuous timeline remains the source of truth.

Preserve:
- stable section IDs
- stable track IDs
- stable range/change IDs
- section bar lengths
- cross-section ranges
- open-ended presence
- derived enter/leave semantics
- downstream Skeleton Session → Draft → Bounce dependencies
- browser-history navigation behavior
- V4 saved projects through migration

Do not recreate separate Parts / Enters / Leaves state.

Internally, timing may continue to support fractional offsets for future precision even though V5 exposes whole-bar snapping.

If a structural refactor makes the app more maintainable, it is allowed. Do not preserve the single-file monolith merely out of habit, but keep GitHub Pages deployment simple and avoid unnecessary frameworks/tooling.

---

# 11. V5 acceptance criteria

A build is not done until these are true:

1. Add Section uses one cohesive section-type + bar-length interface.
2. There is no redundant selected-bar readout and no `Bars bars`.
3. Adding a track creates open-ended presence with no continuation prompt.
4. Open presence automatically includes sections added later.
5. There is no permanent Cut button and no choose-a-cut-bar modal.
6. Presence can be trimmed directly with touch-friendly handles.
7. Selecting presence never creates the old ugly blue end-cap highlight.
8. No essential interaction requires accurately tapping a skinny line.
9. `+ Change` shows common change actions on one screen; no category drill-down is required to reach Widens/Narrows/Louder/Softer/etc.
10. Transition Cue is removed.
11. Adding a change does not ask start/end-condition questions.
12. A new duration/state change appears across the sensible default span immediately and can then be refined visually.
13. Existing changes can be selected through a large control/chip rather than by hunting for their line.
14. Change editing does not open a redundant details menu that merely repeats visible timing/type data.
15. Mapped changes remain visible in a restrained form when the track is collapsed.
16. Two simultaneous changes plus presence look visually calm and intentional.
17. Track rows contain no `1 change`, `Starts bar 3`, etc. narration.
18. Same-category supersession behaves coherently.
19. Cross-section presence and changes remain visually continuous during section slides.
20. V4 saved data migrates without loss.
21. No console errors in normal flows.
22. The result is comfortable at modern iPhone width and iPad width.
23. Touch targets are forgiving even when visible graphics are visually thin.
24. No debug artifacts or dead V4 UI remain.

---

# 12. Product taste test

Before calling V5 complete, inspect the UI as a user rather than only checking feature correctness.

Ask:
- Does this look like a deliberate product or a prototype?
- Is any text explaining something the visual already communicates?
- Is any permanent button present only because implementation was easier?
- Does the user ever have to understand the underlying data model?
- Can a user make the common edit in one obvious interaction?
- When complexity exists underneath, is the default view still calm?

If an interaction passes automated tests but feels visibly awkward, treat that as unfinished.
