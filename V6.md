## 1. Purpose, scope, and product principles

FIRE helps musicians develop an idea into a finished record. Recreation projects support learning by understanding a reference and rebuilding it through The Map, The Skeleton, The Sounds, The Balance, The Shape, The World, and The Finish. Original projects remain the primary long-term product; their existing semantics must survive this work.

V6 is a coherent interaction/design generation, not a collection of cosmetic V5 fixes. Its scope spans orientation, hierarchy, reusable components, reactive progression, direct timeline editing, and screen depth across the existing application. It retains the continuous musical model and existing implemented workflow rather than inventing later phases.

Two principles govern every screen:

> FIRE should show the musician the music, not the database underneath the music.
>
> FIRE assumes the music keeps doing what it was doing. The user documents only meaningful change.

The interface must be calm, deliberate, precise, premium, native-feeling, and touch-first. Strong hierarchy, stable geometry, immediate feedback, progressive disclosure, and predictable navigation should make routine work understandable without instructions. Use [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/) and creative applications such as Logic Pro/GarageBand as interaction references, without imitating Apple branding or importing unnecessary DAW machinery.

### Scope boundaries

- Redesign existing Projects, Recreation home, Map, Structure, Tracks, Section Study, Review Map, Skeleton, Session, Draft, Bounce, Roadmap, Notes, and existing New Project/Original surfaces as specified below.
- Do not implement The Sounds or any later phase, a new Original workflow, audio playback/editing, new project management, beat-level controls, or a new change taxonomy.
- Do not add React, Vue, a backend, database, build pipeline, or runtime dependencies without a later explicit decision.
- Keep plain static GitHub Pages delivery. Application files must remain deployable together without a build step.
- Prefer presentation/interaction changes without schema changes. Never simplify UI by deleting musical capabilities or existing data.
- No V6 application code, tests, migration, localStorage writes, production changes, or activation-document edits belong in this specification PR. Only `V6.md` is added.

## 3. Information architecture and navigation

### 3.1 One hierarchy

**Project type → Phase → Checkpoint → Musical content**

Examples: **Recreation → The Skeleton → Draft → Verse / mapped tracks**, and **Recreation → The Map → Section Study → Chorus**. Project identity (song/artist) belongs alongside its project-type context; it is not another interchangeable phase/checkpoint pill.

Use nouns for locations: **Structure**, **Tracks**, **Session**, **Draft**, **Bounce**, **Notes**, **Roadmap**. The title says where the user is; one short supporting sentence says what to do. Remove action-sentence page titles such as “Map the form,” “Identify the tracks,” and “Build the draft.”

The Map home retains three checkpoints: Structure, Tracks, Section Study. **Review Map** is the concluding review location within the Map/Section Study flow, not an automatically added fourth progress item. It must have its own understandable location/title and edit jumps. This preserves the requested three-checkpoint home while making Review discoverable.

The Skeleton has Session, Draft, Bounce. Later Recreation phases remain visible on Roadmap but have no fabricated checkpoint experiences. Original keeps its current workflow and flexible progression rather than adopting Recreation's strict sequence.

### 3.2 Headers and orientation: three separate navigation concepts

**Back = previous. Pill = parent. Roadmap = Roadmap.** These roles must never be overloaded or secretly perform one another's jobs.

Use one reusable header composition:

- Top-left Back follows actual eligible history, with a truthful previous-screen label when space permits.
- The centered context pill opens the hierarchical parent described below, never the multi-phase navigator/Roadmap.
- The primary title identifies the current checkpoint or musical context.
- Quiet positional information follows §3.4; supporting text appears only when useful.

| Current location | Center context | Destination / behavior |
| --- | --- | --- |
| Structure, Tracks, Section Study, Review Map | The Map | Open The Map phase home. |
| Session, Draft, Bounce | The Skeleton | Open The Skeleton phase home. |
| The Map or The Skeleton phase home | Recreation | Open the current Recreation project home. |
| Recreation project home | Recreation | May be a static context badge; do not invent another level to keep it tappable. Leaving the project uses explicit Back to Projects. |
| Projects | FIRE branding/context | Need not be a navigation control. |

V6 intentionally replaces V5's phase-pill-to-multi-phase-navigator behavior. The Map pill means The Map home; it must not open Roadmap or a phase-selection sheet as a hidden secondary meaning. Parent access remains subject to current eligibility/route safety.

**Roadmap** is an explicitly labeled destination, primarily on the Recreation project home. A quiet Roadmap action may appear on phase homes where useful. Do not permanently add it to checkpoint work screens such as Draft, Tracks, or Section Study without a strong usability reason. It is neither Back nor Up. After Bounce, use **View Roadmap** while The Sounds has no implemented workflow; only a later approved Sounds implementation may justify **Continue to The Sounds**.

Do not add persistent breadcrumb strings such as `Recreation > The Skeleton > Draft`. Truthful Back, the parent pill, current title, and contextual progress provide orientation without another competing hierarchy display.

### 3.3 Back, Next, disclosure, and route entry

- Visible Back follows the actual previous eligible screen, not a fixed workflow predecessor or hierarchical parent. Tracks → Section Study returns to Tracks; direct The Map home → Section Study returns to The Map; The Skeleton home → Session returns to The Skeleton; Session → Draft returns to Session when that is the actual prior eligible route.
- Browser Back/Forward and FIRE's visible Back must remain coherent. Parent-pill navigation does not redefine or overwrite the actual entry history.
- Next advances an eligible workflow step; it does not dismiss an editor. Done closes an editing state/sheet. An inline disclosure is not a route.
- Keep browser history coherent across project/phase/checkpoint entry. Section selection and Draft disclosure must not add route-depth or overwrite the remembered checkpoint entry.
- Every attempted route, including Back/Forward, parent access, initial/restored history, and review jumps, uses the same current canonical eligibility/availability policy as visible controls.
- If a prior/restored route is no longer eligible, resolve safely to the nearest meaningful eligible prerequisite/phase destination in the same project. Avoid loops and competing Back behavior; retain data and valid work rather than deleting it to repair navigation.
- Review edit jumps retain a usable return destination. Leaving an invalidated page must not discard notes or create fake completion.

### 3.4 Contextual progress by hierarchy level

**Home screens = visual progress. Working screens = quiet positional progress. Nested musical work = local musical position.** Do not display multiple competing progress systems simultaneously.

| Location | Useful progress / orientation | Avoid |
| --- | --- | --- |
| Recreation project home | Current Phase, phase title, and journey position such as **The Skeleton · Phase 2 of 7**; an optional restrained thin indicator. | Checkpoint counters by default; include one only if it genuinely clarifies the Current Phase summary without clutter. |
| The Map phase home | Currently valid completion across Structure / Tracks / Section Study: a quiet `1 of 3` count and/or restrained thin bar. The checkpoint list is the strongest detailed complete/current/locked indicator. | Redundant decoration or another seven-phase progress system competing with checkpoint progress. |
| The Skeleton phase home | The equivalent valid-completion count/bar across Session / Draft / Bounce, with the list dominant. | Layered or inconsistent progress systems. |
| Normal checkpoint work | Quiet position when useful: Structure `1 of 3`, Tracks `2 of 3`, Session `1 of 3`, Draft `2 of 3`, Bounce `3 of 3`, alongside the phase context and noun title. These counters indicate location, not completion. | Another full progress bar or dashboard on each work screen. |
| Section Study | Phase context **The Map**, quiet **Section Study · 2 of 8**, dominant musical title **Chorus**, and **8 bars**. Prioritize local song-section position. | Simultaneous checkpoint `3 of 3` and section `2 of 8` counters in the same header. The Map home already establishes its checkpoint position. |
| Review Map | Clear **Review Map** title and The Map parent context; concluding review state of the three-checkpoint Map workflow. | A fictional fourth checkpoint or conflicting progress counts. |

All completion counts, bars, indicators, checkpoint states, availability, and route guards derive from the same current canonical state (§6). Positional counters derive from that state's actual order/location; they must never masquerade as “complete” counts. Displayed completion is valid current completion, not historical interaction. Previously entered Draft work can remain stored when a Map prerequisite becomes invalid, while visible valid progress correctly reflects the dependency.

## 4. Shared visual and component system

### 4.1 Visual hierarchy

Use neutral graphite/near-black surfaces, crisp readable type, restrained accents, and musical category colors subordinate to neutral presence. FIRE is not themed around Smithereens. Avoid foggy glass, decorative gradients/glow, dense grid decoration, and competing neon tracks.

Prefer open layouts, typography, spacing, grouped lists, and a small number of separators. A bordered rounded rectangle is not the default wrapper for every concept. Reserve important cards for a genuinely dominant grouping, such as the current phase. Secondary Roadmap/Notes destinations must not look equally important.

Establish shared spacing, radii, typography, control heights, selected/disabled/focus states, and sheet padding before screen-specific variants. Variants must preserve a recognizable family across iPhone/iPad and Original/Recreation. One clear primary action per screen where applicable; label it with the actual next destination/action.

### 4.2 Component contract

| Component | Appropriate use | Required behavior / avoid |
| --- | --- | --- |
| Primary action | Principal eligible step or deliberate commit, e.g. Add Section / Next | One main emphasis; visible eligibility; stable dimensions. No oversized unrelated Next beside an unrecognizable Previous. |
| Secondary/quiet action | Edit, Cancel, contextual Start/Stop, Roadmap, Notes | Lower visual weight, full target size; not a competing primary card. |
| Checklist row | User-completed tasks: First Listen, verification, Session elements, Draft parts, Bounce | Whole-row target, one consistent completion indicator, immediate feedback. Derived completion rows are not manually checkable. |
| Single-select control | One of 2–5 closely related choices | Stable segmented-style group; mutually exclusive selected state, no geometry change. |
| Multi-select control | Tracks, present-track Focus, existing Original choices | Equal-height toggle rows/tiles/check controls; stable grid/list geometry and non-color selection cues. |
| Segmented control | Feel dimension or `4 / 8 / 12 / 16 / Custom` | Cohesive group, not floating egg pills; tonal selection, persistent labels, no reflow/scale. |
| Disclosure row | Draft sections, contextual Notes, Review sections | Whole-row target; expanded state exposed accessibly; expand in place and preserve scroll/context. |
| Standard grouped list | Setup fields, checkpoints, Session checks, secondary destinations | Shared alignment, separators only where useful, no nested card per row. |
| Important summary card | Current phase or a genuinely important review grouping | Stronger hierarchy used sparingly; do not surround all secondary items with it. |
| Bottom sheet | Add/Edit Section, Add Change, existing project actions, rare contextual precision controls | Shared lifecycle and stable layout; no nested taxonomy drill-down or automatic text keyboard on edit opening. |
| Timeline range/state | Presence and continuing state changes | Meaningful occupied span; continuation clips without false terminal graphics. Presence remains primary. |
| Timeline boundary | Real start/stop of a state | Graphic means an actual musical edge; enlarged target, whole-bar editing, accurate feedback, no fabricated viewport cap. |
| Change chip | Select an existing mapped change / + Change | Large labeled selector, non-color selected state, direct timeline editing rather than a details menu. |
| Toast / Undo | Reversible routine musical edits/removal | Quiet, reachable, unobstructive; restore affected musical data and dependent progress together. Never overwrite subsequent edits with a stale snapshot. |

For option sets larger than five, use an adaptive equal-height grid/list rather than squeezing all choices into a segmented group. Labels may wrap accessibly, but selection itself must not change geometry. Multi-select and single-select semantics must remain distinguishable.

### 4.3 Stable selection and press feedback

Selection must not resize a control, move adjacent controls, change border dimensions, reflow a sheet, or shift a drag target. Use tonal fill, opacity, an inset treatment, or a stable check indicator. Do not use scale transforms as press feedback. A handle's apparent position and hit geometry must stay aligned while pressed.

## 5. Sheets, focus, and input lifecycle

All sheets share corner-radius tokens, horizontal padding, vertical rhythm, grabber treatment, dismissal, and reduced-motion behavior. The grabber is a familiar affordance, not the only way to dismiss. Provide a clear Cancel/Done action; sheet/background dismissal must not erase committed data or accidentally create incomplete objects.

- Open Edit Section with focus on a suitable non-text container/title/control. Do not autofocus its name input or summon the iOS keyboard. Text editing begins only when the user intentionally selects the field.
- Do not automatically request a keyboard in other sheets unless text entry is clearly the action intentionally requested.
- Keep the sheet, controls, scroll position, and focus stable for ordinary selection updates. Do not reconstruct the entire sheet DOM when a bar/type choice changes.
- Custom input disclosure is an intentional layout change, not selection jitter. Reserve sensible space or expand predictably without resetting scroll/focus or changing the selected button's size.
- Trap modal keyboard focus appropriately, label the sheet, support Escape and explicit close, and return focus to the opener or a logical surviving control. Do not focus hidden content or restore to a detached node.
- Preserve the active text field, caret/selection, composition, and keyboard while saving live input. Do not fix reactive gating by rerendering the whole page on every keystroke.
- Respect safe areas, visual viewport changes, orientation changes, and keyboard occlusion. Controls must remain reachable on a small iPhone; large sheets can scroll internally without dragging/scrolling the page underneath.
- Do not let an Undo toast obscure a sheet's dismissal/primary action or receive hidden background focus.

## 6. Current-state progression and route guards

### 6.1 Canonical-state rule

**Progress and gating share one source of truth: current canonical state.** Every progress count/bar, completion indicator, checkpoint state, availability state, and route guard must derive from it. Anything that gates progress must be derived from current canonical state. Saved user attestations/checks remain data; derived completeness/eligibility must not be duplicated as independent persistent booleans or stale render snapshots.

A required input change must, in the same coherent update cycle:

1. Update the canonical model from the actual input, including clearing a value.
2. Validate the current value and save appropriately without disrupting typing.
3. Invalidate only logically dependent confirmations/work.
4. Recalculate completion, eligibility, counts, and implementation availability.
5. Update affected controls/progress immediately in place.
6. Revalidate the current route and all attempted transitions against that same state.

No blur, route round-trip, unrelated setting toggle, storage reload, or full-sheet recreation may be necessary to make the system recognize the current input. Fast input and rapid clicks must not race stale eligibility.

Keep these concepts separate:

- **Completion:** Does the canonical evidence satisfy this requirement and its required dependencies now? Retained historical check records alone are not valid current completion.
- **Eligibility:** Are this screen/action's current prerequisites satisfied?
- **Implementation availability:** Does the destination actually exist?

A stored completed Draft does not make an incomplete Session eligible or permit downstream progress to appear currently complete when its required dependencies are invalid. A future phase becoming conceptually next does not make its screen implemented. Preserve valid stored work while correctly restricting current forward access.

### 6.2 Dependency and gate inventory

| Requirement / destination | Canonical evidence and gate behavior |
| --- | --- |
| Song Setup → Structure | Reference attestation, current valid BPM, required meter, grid alignment, and First Listen must all be satisfied. Clearing any required value immediately removes forward eligibility, even if Structure was previously verified. |
| Tempo/BPM | Use the live field/model value, not a cached truthy text fragment. Empty, whitespace-only, nonnumeric, nonfinite, or nonpositive values cannot satisfy Tempo. Support a valid decimal tempo without inventing an arbitrary new BPM ceiling. Do not round or silently rewrite existing saved musical data. |
| Structure completion | Every retained section has valid name/length and a stable identity; explicit Structure verification is still required. Reorder/length edits invalidate the relevant verification and dependent positions. |
| Tracks | The selected track palette contains the required mapped choices. Adding/removing custom tracks updates counts, eligibility, and requirements immediately; no parallel Unidentified list. |
| Section Study access | Current Setup/Structure/Tracks prerequisites, not an old “already complete” exception. Existing analysis remains stored when access is temporarily gated. |
| Individual study sections | Current ordered sections, valid lengths, presence or explicit silence, all five Feel choices, and selected present-track Focus or No clear focus. Preserve sequential forward progression and access for appropriate repair/backward editing. |
| Review Map / Map completion | Derived study completion and track-use requirements plus Map Verified and Teach It Back. These checks are user attestations, not substitutes for current prerequisites. Preserve the existing requirement that every selected track appears somewhere before final completion; unused tracks get the existing concise correction link. |
| Skeleton entry / Session | Current Map completion plus implementation availability. Session completion derives from each currently required track and section-marker check, not a single global marker toggle. |
| Draft | Current Map and Session prerequisites; per-section required tracks derived from presence. A section completes automatically when its required parts are done; intentional silence uses the existing silent-section rule. |
| Bounce | Current required Map/Session/Draft state; Export draft and Listen start to finish are separate attestations. Listen requires export. No old Bounce check may bypass an invalidated prerequisite. |
| Future phases | Distinguish conceptually next from implemented. No functional route beyond the implemented experience; use Roadmap honestly. |

Progress and eligibility updates must cover phase-home counts/bars, completion indicators, checkpoint lists, contextual positional indicators, parent-pill links, explicitly labeled Roadmap destinations, section tabs, Next/Continue buttons, review jumps, and browser-restored routes. A disabled button alone is not a route guard. Recheck in `go`-equivalent navigation, initial/history restoration, `popstate`, and mutation-driven route repair. A rejected route preserves the project and content; it returns to an eligible place to repair the requirement instead of presenting a dead workspace.

### 6.3 Invalidation without needless loss

Centralize mutations and invalidation. Reuse existing dependency semantics unless a reviewed change is necessary:

- Setup changes update eligibility and invalidate Map verification as appropriate. Temporarily clearing BPM must not wipe notes, timeline data, or unrelated valid Draft check records.
- Structure edits invalidate Structure/Map verification; positions/lengths invalidate affected DAW markers and affected work while preserving unrelated section-ID-bound progress.
- Presence edits invalidate the affected track/section span and Bounce, including downstream sections of an open tail. Focus must never reference a now-absent track; explicit silence must not coexist with actual presence.
- Arrangement/performance changes (Doubles, Pattern shift, Register shift, and relevant preserved legacy cues) invalidate affected Draft requirements as before. Width, level, and effect observations must not force a rough arrangement rebuild.
- Draft requirement/check changes invalidate Bounce. Clearing Export makes Listen incomplete/ineligible as before.
- Notes and disclosure/selection changes do not invalidate musical completion.
- Undo restores the musical edit and its dependent verification/completion state consistently. A newer saved edit must not be overwritten by an obsolete Undo action.

Do not collapse valid-completion recalculation, eligibility, and destructive invalidation into one operation. Locking a route or correcting visible progress is not permission to delete already-recorded music or progress. If a required BPM becomes empty, eligibility, dependent checkpoint state, valid completion counts/bars, and route access update immediately and agree; restoring a valid BPM recalculates all of them immediately. No independent cached progress value may say “2 of 3 complete” while the canonical completion/gating policy disagrees. Apply this invariant to every prerequisite, not only Tempo.

## 7. Screen requirements: project entry and The Map

### 7.1 Projects, New Project, Recreation home, Original

**Projects:** Use a clean list of whole-item navigation targets showing project type, song title, artist when applicable, and current phase/meaningful progress. Remove redundant “Open” text/actions when the row already communicates navigation. Integrate one New Project/+ affordance in the header. Use the standard overflow action sheet/menu and preserve existing actions, including deliberate confirmation for project deletion. Do not add search, folders, collaboration, or other project-management scope.

**New Project:** Clearly distinguish Original and Recreation with shared, stable single-select controls. Keep Recreation creation concise in one clean sheet/page unless a real need justifies depth. Integrate title/artist entry consistently; do not summon a keyboard merely by opening a selection/edit surface. Preserve existing stored project types, including internal `study` compatibility, rather than migrating solely for a public label.

**Recreation home:** Song, artist, Recreation context, dominant current phase, and seven-phase journey progress (for example The Skeleton, Phase 2 of 7) must answer “What project? Where am I? What next?” A restrained thin indicator may accompany it; checkpoint counters are not the default here. Recreation may be static context on this home; explicit Back to Projects leaves the project. Keep the next-phase preview quiet. Roadmap and Notes are secondary grouped destinations, not equally strong cards. When later phases are not implemented, current/next messaging must not promise their workspace.

**Original surfaces:** Apply shared visual, component, sheet, input, and navigation consistency to existing Original overview, Spark, Notes, and Roadmap surfaces. Preserve Original's current semantics and flexibility; do not invent a new Original workflow, strict Recreation gates, new Notes system, or additional product logic.

### 7.2 The Map home

Keep full Song Setup directly above the three checkpoints: Structure, Tracks, Section Study. Setup consists of Reference, Tempo/BPM, Meter, Grid, and First Listen. Use cohesive grouped controls rather than a stack of decorative cards. Do not hide the existing necessary setup behind an extra navigation level.

On The Map phase home, center Recreation returns to the current project home. Checkpoint progress belongs to the three-checkpoint grouping: quiet valid-completion count such as `1 of 3` and/or restrained thin bar, with the checkpoint list the strongest detailed indicator. Recompute progress and eligibility live from the same canonical policy; do not add redundant decoration. The Section Study checkpoint may lead to its completed review location when appropriate, retaining edit access and honest completion.

### 7.3 Structure

Title **Structure**, with quiet checkpoint position `1 of 3` where useful and The Map parent pill; suggested support “Map the song's sections.” Do not add a work-screen progress bar.

Use stable ordered rows: index, section name, bar length, permanent drag handle. Keep row tap editing distinct from reorder-handle drag; normal scrolling elsewhere must work. Preserve smooth Pointer Events reordering, cancellation, stable IDs, and a discoverable non-drag alternative.

**Add Section:** One cohesive sheet. Intro, Verse, Pre-Chorus, Chorus, Bridge, Instrumental, Outro, Custom appear as an adaptive grid/list of equal-height controls. Eight choices are not one segmented control. Selection updates in place with no egg shapes or reflow. The name field appears only for Custom.

Bar length is one segmented-style group: **4 | 8 | 12 | 16 | Custom**. Only Custom reveals a numeric whole-bar input. Do not repeat the selected standard length as another field/readout. Add Section inserts nothing until name/type and length are valid; repeated names retain numbering and appropriate previous-length suggestion behavior. Selection must remain editable before insertion.

**Edit Section:** Compact rename, length, appropriate reorder alternative, and Remove. Opening never autofocuses the name field. Keep meaningful deletion confirmation/data safety. Verification remains after the list, distinct from final Map verification. A layout update must not detach section notes or ranges.

### 7.4 Tracks

Title **Tracks**, with quiet checkpoint position `2 of 3` where useful and The Map parent pill; support “Identify everything that appears somewhere in the song.” Do not add a work-screen progress bar.

Use the shared multi-select tiles/rows/check system, with stable dimensions, clear non-color selected state, and forgiving targets. Adapt the grid for iPad rather than enlarging a cloud of capsules. Common and custom tracks belong in the same palette. Integrate custom naming/commit as a quiet extension of the group, not an unrelated bulky input-plus-Add form. Preserve existing musical identities, downstream requirements, and removal safeguards.

## 8. Section Study and Arrangement

### 8.1 Musical viewport and layout

Section Study remains one focused viewport into the continuous song timeline. Keep the current section name and length dominant, quiet Section Study position, fixed track ordering, and restrained directional movement between sections. Tracks must not jump vertically merely because presence differs between sections. Only one track is expanded for editing at a time.

Collapsed rows show the track name, neutral presence, and restrained duration/point-change cues. Do not add “1 change,” “Starts bar 3,” or equivalent narration to collapsed lanes. Two simultaneous changes plus presence must stay legible and calm through position/thickness/shape as well as color. The grid/ruler supports reading and snapping; it is not the dominant object or a field of mandatory tiny buttons.

### 8.2 Boundary truth: music versus clipping

**A boundary graphic represents a real musical boundary. A viewport edge is not automatically a boundary.** Selection must never contradict this rule.

| Musical state in the visible section | Display |
| --- | --- |
| A track actually starts here | Real start boundary at its musical position. |
| It began before this section | Presence enters at the left edge with no fake leading cap/handle. |
| It actually stops here | Real end boundary at its musical position. |
| It continues into later sections | Presence exits the right edge without a fake terminal cap/handle. |
| It remains open at the current song end | Open continuation, not a terminal cap merely because no later section exists yet. |
| A true stop/start is exactly at a section edge | Show that actual boundary; do not remove it merely because it coincides with clipping. |
| A duration change is constrained by parent presence | Reflect its effective musical extent, not just whether its stored end is null. |

Distinguish a temporary placement cursor/target from a committed musical boundary using labeling and visual treatment. A placement target is not drawn as an existing terminal cap. Apply the same truth to duration/state changes, selected states, collapsed states, section slides, and reduced-motion transitions.

### 8.3 Start, stop, and resume instead of Split

Presence remains open-ended by default. Adding an absent track with the clear + affordance starts it at the current section start by default without a continuation prompt. Choosing a later start/resume position creates an open state at that musical position. Later-added sections inherit open presence automatically.

The normal interaction contract is:

1. Select a track or its meaningful presence area through a generous row-sized target. Closely spaced existing pieces must have forgiving selectors; do not require choosing a 4–8px line.
2. Reveal real editable musical boundaries and only relevant actions. Dragging an existing start/stop changes that actual boundary and snaps to whole bars, with lightweight accurate position feedback.
3. For a continuing/open state with no actual visible stop, expose a discoverable contextual **Stop** placement affordance. It must not look like an already-existing terminal edge. Let the user place the stop at a whole-bar boundary through the lane's large targeting surface or a large movable preview target.
4. Commit the chosen stop as a real boundary. It then has a real end handle that can be adjusted directly. Make the edit reversible with Undo.
5. In an off portion, expose contextual **Start**/resume placement so the musician can activate the track again later. Internally another range may be created; the UI describes the music as playing, stopping, and coming back.
6. Normalize adjacent coverage with no actual absence. Do not keep fake stop/restart edges at the same instant.

A concrete walkthrough must be achievable without model terminology: Drums plays from the beginning, stops after bar 4, resumes at bar 7, and continues forward. The default UI must never ask the user to “split a range,” enter From bar/Through bar, or Add gap. Do not hide the old Split form in another menu and call that a redesign.

Stop/start placement must be discoverable before a gesture is attempted. Position previews make the intended boundary explicit before/while committing. A normal touch gesture may commit on deliberate release; cancellation leaves canonical data unchanged. Do not silently add a stop by merely selecting a continuing state or by tapping outside it to deselect.

Rare precision/accessibility operations may use contextual controls described in §11. They must not reintroduce permanent **Start 1 − + / End ∞ − +** readouts or make the common workflow a timing form. Internal gaps/multiple ranges remain fully supported, including preexisting V5 data.

### 8.4 Whole-bar semantics and editing safety

Use shared boundary math for presence and changes. A section with eight bars has boundaries before bar 1 through after bar 8. Starting at boundary 0 means bar 1; stopping at boundary 4 means after bar 4/before bar 5; resuming at boundary 6 means bar 7. Feedback must distinguish a start bar from an end-after-bar to avoid off-by-one edits.

- Quantize intentional V6 edits to whole bars, not imported/stored fractional anchors that the user has not edited.
- Do not permit inverted/zero-length ranges or events outside parent presence. Treat a no-op and a canceled gesture as no mutation, no invalidation, and no Undo-history consumption.
- Respect cross-section anchors: selecting a later viewport does not create a fake local start. Editing a visible real edge changes that edge, not an unrelated clipped range or another track.
- Keep object identity and dependent state coherent through extension, touching/merging pieces, re-entry, cancellation, and Undo.
- Undo protects routine placement, timing changes, and removal without confirmation modals for each small edit. It must restore related observations/progress if a presence edit affected them.
- Long-press/double-tap may be optional accelerators, never the only route to an essential action.

**+ Change** remains one sheet with all common actions directly available under quiet headings. No category drill-down or Duration/Moment classification. Choosing an action creates the sensible existing default immediately across the applicable selected/current visible presence, closes the sheet, and lets direct editing refine timing. Track changes stay within parent presence; Mix changes are not forced onto an instrument.

Existing large labeled change chips select a change rather than opening a redundant timing/details menu. ## 11. Accessibility and touch contract

- Approximately 44pt-equivalent touch targets (at least approximately 44 CSS px in the default web presentation), even when a visible line/marker is much smaller. Do not count clipped/overlapping areas as a usable separate target.
- Provide visible discoverability, accessible names, focus indicators, pressed/selected/expanded states, and logical reading/tab order. A label says the musical action/object, not a database ID.
- Presence selection, overlapping/short range selection, change selection, boundary placement, point movement, reorder, removal, and Undo all need a forgiving non-drag path. Contextual position selection/accessible adjustment is allowed; persistent Start/End +/- readouts and Split/gap forms are not the default alternative.
- Sparse hit areas must not make an essential boundary impossible to select. When many whole bars cannot fit separate large targets, provide a contextual accessible precision path rather than silently shrinking targets to grid lines.
- A real boundary's accessible adjustment reports an unambiguous start/stop musical position and updates the same mutation path as dragging. Keyboard/screen-reader users must be able to place a new stop or later start without an invisible gesture. Do not force mouse-style dragging as the only implementation.
- Use shape, labeling, position, and/or thickness as well as restrained color for musical distinctions. Disabled, completed, current, and selected states must not rely on color alone.
- Support VoiceOver/screen readers, keyboard input where applicable, reduced motion, readable contrast, and text enlargement without losing required actions.
- Focus and DOM must remain stable through selection, live input, disclosure, Undo, and sheets. Routine edits must not summon the iOS keyboard unexpectedly or scroll the page away from the edit.

## 12. Data preservation and eventual implementation architecture

Keep `production-projects-v1`, all existing projects, and V4→V5 migrated records. - Presentation changes must not round all saved positions, flatten section-relative anchors, close open tails, lose legacy cues/custom events, or erase already-completed valid work.
- Start/stop/resume operates on existing ranges. Entering/leaving remains derived from presence; do not create separately persisted Parts/Enters/Leaves or on/off booleans beside the timeline.
- Real splits/merges preserve surviving identities and introduce new identities only where genuinely necessary. Selection/disclosure/focus state is transient and distinct from musical data.

- Normal startup and backup import use the same reviewed normalization/migration path. Reject malformed input without replacing the live project set; intentionally empty project sets stay empty. Preserve import/export compatibility and do not invent schema churn for visual changes.

Favor shared canonical-state selectors, a single eligibility/route policy, reusable components/rendering, in-place updates, centralized musical mutations/invalidation, and a clear separation between data semantics and presentation.
